# DP12c and DP18 cases: TX simulate per RF port, the node beacon and objects

Status: written offline for the next DV-Router image (DP12c + DP18, wip 33a6d6e, after SECRELOAD1 and RFWD1). **Nothing here has run on a rig**: there is no image yet.
What the cases check comes from the DV-Router documents (`data.md` 9.5 "Built (DP18)", 10.x "Built (DP12c)", 13.1, `config.md` `[edges.aprsis.beacon]` and
`[[edges.aprsis.objects]]`, `radio.md`, `admin.md`, `status.md`) and from the DV-Router review 232 of the change (`review-232-dp18.md`, read only, cited by name).
Case files `cases/test_dp18_origin.py` (private aprsc), `cases/test_dp18_rf.py` (AX.25 edge, two fake TNCs) and `cases/test_dp18_config.py` (host side, `cfgload`, no rig; helpers `dvtest/dp18cfg.py`), helpers `cases/dp18_support.py`, builders in
`dvtest/proto/aprs.py` (`position_report`, `object_report`, `lat_text_e7`, `lon_text_e7`, `parse_object`), snippets in `rig/config/dv-router/`, unit tests
`cases/unit/test_dp18_support.py` and `cases/unit/test_proto_aprs.py`. Expected lines are built from the RENDERED config of the run with hand-written APRS101 shapes, never from
DV-Router's encoder.

**Skip rule.** Every case skips with the reason on an image without DP12c / DP18. The probe is a capability, not the image tag: the served configuration schema
(`GET /api/v1/admin/schema`) must contain `simulate`, `beacon` and `objects` (`dp18_support.schema_has_dp18`). A run that lacks the shape (snippet) skips as well.

## Strict (`DVT_DP18STRICT=on`)

The default run of R stays comparable across images. The switch adds the asserts that depend on the APRS-IS leg working TOGETHER with `rf_ports`, on counter conservation
and on the strict floor; it is passed to the tester by `rig/compose.yml`. Without it each strict case skips naming the switch.

* **Known product defect, the reason for the switch.** `dv-edge-aprsis` exits with a configuration error as soon as an object or the beacon has `rf_ports`: `crates/edge/aprsis/src/shell.rs` validates
  the file with `Config::default()` plus only `edges.aprsis`, so the AX.25 port the RF copy names does not exist in what it validates.
  The worker then finds no `aprsis-` edge and counts `dv_pkt_origin_total{result=no_edge}` for every report, and nothing reaches the aprsc. Confirmed by DV-Router; fixed by their unit DP18b (merge d3c6e531, a later image): an igate with `rf_ports` keeps its APRS-IS edge, the RF edges validate the full snapshot, and `no_rf_edge` counts one per withheld RF copy. On a DP18b image all three strict cases are expected to PASS; a failure there is a product finding.
  On an image with the defect the strict `no_edge` case and the strict aprsc case FAIL; the conservation case is expected to pass there (the worker emits the RF copy whether or not an APRS-IS edge exists, `core_origination.rs`).
* **Conservation terms** (read per RF port, deltas since the start of the observation): copies = `dv_pkt_origin_total{result=generated}` of each kind times the RF ports of its reports (the
  case computes it from the rendered config and skips, saying so, when a report names a port other than the one read or the reports of a kind differ in their ports); terminal =
  `dv_edge_rf_tx_total` results `sent`, `simulated`, `sent_over_budget` and every result that starts with `dropped_`, summed over the scheduler classes; withheld = `dv_pkt_origin_total{result=no_rf_edge}` (a term of its own since d3c6e531); queued = the change of the gauge
  `dv_edge_rf_queue{port}` (frames queued for the physical transmitter). `delayed` is NOT terminal (the copy is still queued, or ends as `sent` or a `dropped_*`).
  Without `DVT_TXCNT1B=on`, `rf_fenced` is NOT a term (checked against DV-Router 7710756; with the switch it is, see the TXCNT1B bullet): it is `dv_edge_drops_total{reason=rf_fenced}`, an edge counter without a port label and not a `dv_edge_rf_tx_total` result, and data.md 10.8 says a fabric fence does not undo a scheduler reservation. A frame discarded while held (`TxCore::fence`) stays in the scheduler queue and the gauge until the scheduler releases it (`sent`) or expires it (`dropped_ttl`), a released permit lost to a fence was already counted `sent`, and a client or render frame refused while fenced never reaches the scheduler; adding it would count those copies twice. The case reads it (0 on an image without it) and records it in the `RECORD` line only, with no assert on its value (the RFSAFE1 startup fence of about 3.2 s may count frames; the first report is due after one full interval).
* **Hard asserts.** Under the switch `no_edge` / `no_rf_edge` = 0, `sent_over_budget` = 0 and the conservation are hard asserts. The conservation case writes ONE `RECORD` line before it asserts that names every term (generated per kind and result, copies expected, sent, simulated, sent_over_budget, delayed, each `dropped_*` and their sum, terminal, the queue gauge at the start and now, and the unaccounted difference, then the recorded-only `rf_fenced` edge drops), so on the DP18b image a mismatch is a product accounting finding that shows exactly which terms differ. `no_rf_edge` is printed twice: inside the origin map and as its own term. Also recorded (NOT in the equation, so that a difference can be matched against them): the worker-side RF output counters `dv_pkt_rf_downlink_total{kind=aprs-info,result=not_heard|rate|dedupe}` and `dv_pkt_rf_drop_total{reason}`, where a copy can also be lost before the scheduler (data.md 9.5: RF copies pass the worker dedupe and the per-port packet rate).
* **`DVT_TXCNT1=on` (DP18-o txcnt1).** A second, independent switch (passed by `rig/compose.yml`, listed in `dvtest/target.py`) for the DV-Router unit TXCNT1 (commit 7710756, image wip-bd3ceb9): `dv_edge_rf_tx_total{result=delayed}` counts the first hold of a queued copy once (`scheduler.rs` `record_wait`, a per-copy `delayed` flag), not every dispatch poll. The case `test_dp18_o_txcnt1_delayed_counts_frames_not_ticks` reads the same `objects_run` observation and asserts, on the `delayed` delta summed over the classes of the port, the UPPER bound `delayed <= RF copies expected + queue gauge at the start` and, when the start gauge is readable, the LOWER bound `delayed >= dropped_ttl - queue gauge at the start`. The lower bound is the only one the code proves: a copy that expired waited its whole TTL, and a dispatch that releases nothing holds every queued copy while a release sets busy/gap time so the next dispatch holds the rest; a copy still queued at the end may be just enqueued and not yet polled, a `dropped_queue` copy never waited, and a `sent` copy may leave at its first poll. It writes one `RECORD` line first (every input: delayed, copies, `dropped_ttl`, `dropped_queue`, `sent`, `sent_over_budget`, `simulated`, queue gauge start / now / delta, frames at the TNC, the `rf_fenced` edge drops). On wip-125de6f it FAILS the upper bound (+8932 in 27 minutes of run R with 7 frames waiting, 8932 > 22). `delayed` is still not terminal and stays out of the conservation sum.
* **`DVT_TXCNT1B=on` (DP18-o strict conservation, DP18-o txcnt1b labels).** A third independent switch (passed by `rig/compose.yml`, listed in `dvtest/target.py`) for the DV-Router unit TXCNT1b (commit 051a4516, merged, NOT in any image yet; an image with it also satisfies TXCNT1). Read at 051a4516 (`docs/design/data.md` 10.8, `docs/design/status.md` Metrics):
  `data.md:2386-2392`: "`generated = sent + dropped_* + canceled before release + still queued`, where `sent` in this equation is all mutually exclusive release results (`sent`, `sent_over_budget`, and `simulated`) and `dropped_*` sums terminal results only. Cancellation before release is counted once in `dv_edge_drops_total{reason=rf_fenced}`: a fence or orderly shell stop removes both payloads and scheduler entries, without refunding already charged airtime or allowing ghost releases after recovery." `data.md:2408-2410`: a released permit's later `rf_fenced` or modem `dropped` outcome "is a downstream diagnostic, already covered by its scheduler release in this equation, and must not be added again". `status.md:681-688` (the Metrics section, "For a selected cohort of scheduler-submitted RF copies") adds that the `rf_fenced` aggregate "also includes pre-admission and post-release refusals, so only the queued cancellation cohort belongs in this sum".
  * **What changes.** Under the switch the conservation case uses `copies = sent + simulated + sent_over_budget + sum dropped_* + no_rf_edge + delta dv_edge_rf_queue + canceled`, `canceled` = the delta of `dv_edge_drops_total{reason=rf_fenced}` over the run. Because the black box cannot split that aggregate into the queued cancellation cohort and the post-release / non-copy refusals the docs exclude, the term is an UPPER bound: the unaccounted copies (`copies - accounted - queue delta`) must lie in `0 <= unaccounted <= rf_fenced delta`. It is exact (unaccounted equals the term) whenever no extra refusal happened, in particular it must be 0 when `rf_fenced` is 0. A negative value (more results than copies) or an unaccounted count above the fence term FAIL. The `RECORD` line is labelled "(TXCNT1b equation)" and ends with `unaccounted after the term` (0 = exact; negative = slack of extra refusals counted in the aggregate). The older image: a fenced copy stays queued and later ends as `sent` or `dropped_ttl` (7710756), so the term would count it twice: this is why it is switch-gated. Without the switch the equation and the verdicts are exactly the ones above.
  * **How a drained copy is counted.** `tx.rs` `TxCore::fence` now also calls `Scheduler::drain_pending` for every scheduler, and the orderly stop of `shell.rs` calls `tx_core.fence()` too: each discarded payload adds one `rf_fenced` (the edge counter `dv_edge_drops_total`, no port label, NOT a `dv_edge_rf_tx_total` result) and its scheduler entry leaves the queue, so the gauge `dv_edge_rf_queue` drops and the copy never ends as `sent` or `dropped_ttl`. Charged airtime and quiet gaps are not refunded. A broadcast render refused while fenced counts once per target port.
  * **Label set (case `test_dp18_o_txcnt1b_result_labels_are_the_documented_set`).** Reads `hub.text()` after the `objects_run` observation (no extra rig run) and asserts that the set of `result` labels of every `dv_edge_rf_tx_total` series is a subset of the eight documented labels above, in particular that none of `dropped_budget`, `dropped_quota`, `dropped_gap` appears. `rf_fenced` is not a result of this counter (it is a `dv_edge_drops_total` reason; the monitor stage list `SCHED_RESULTS` has it, the metric does not). The failure names the removed labels apart from unknown ones. The hub exports only series the edge has touched, so the check is as strong as the traffic of the run.
  * **Delayed bounds (DP18-o txcnt1): unchanged.** 051a4516 does not change what they rely on: the upper bound (`delayed <= copies + queue at the start`) rests on one `delayed` per copy, which `data.md` still states and the diff does not touch (`scheduler.rs` only adds `DropReason`, `drain_pending`, and the typed drop causes); the lower bound (`delayed >= dropped_ttl - queue at the start`) rests on a TTL-expired copy having been held, and the draining fence only REMOVES copies that would otherwise have ended as `dropped_ttl`, so the bound can only get looser. The data.md addition that budget, quota and gap holds are `delayed` is what the code already did. No change to the case.
  * **GAP: "a render naming a nonexistent port is one invalid refusal" (`txcnt1b_unknown_target_port_is_one_counted_refusal`, `tx.rs` `enqueue`: `unit.port > cfg.port.len()` refused as `invalid`, no copy, no watermark advance).** Not drivable black-box. The `port` field is the destination of a worker-built render unit on `edge/<id>/tx/*` (`data.md` 5.2, `0` = every port), set by the worker from the configured `rf_ports` and from the port of the path; `rf_ports` accepts only configured AX.25 port names (`config.md`, validation refuses others), so no config shape makes the worker name a port the edge lacks, and no UDP client (a DP11e KISS client has its own `channel` refusal in `dv_edge_kiss_frames_total`, a different path) can inject a render unit into the fabric. The refusal counter (`dv_edge_rf_rejected_total{result=invalid}`) is therefore covered by the product unit test only; a rig case would need a fabric-level injector, which this suite does not have by design.

* **Terms that cannot be read** are recorded as `RECORD` lines and are not guessed: a missing `dv_edge_rf_queue` series for the port (only "terminal is not more than generated" is then checked); the frames
  that are in flight between a scheduler release and the modem adapter (counted `sent` at the release; the TNC count is compared in the spread case, not here); two RF ports on one physical (the gauge is
  per physical transmitter: the case reads the first RF port and its snippets use `rf-a` only).
* **The floor** is judged on the object's HMS stamp, which is the generation time, so a queue that delays one release cannot create a false failure; the release times at the TNC are judged only with the
  switch (a queue delay may legitimately shorten that gap). Observing the floor needs two cycles: at least 1330 s with `dp18-rf-floor.toml` (stage F), and R already runs two cycles
  (`DVT_DP18_CYCLES`, default 2), where most of the eleven reports are dropped and few repeat, so F is the clean run.
