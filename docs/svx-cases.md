## 3. What surprised us (every difference from the research note)

The note is right on all layouts; the differences are behaviour it did not
state, a few corrected numbers, and one place where the note's table invites a
wrong implementation.

S1. NodeList (101) is not how a current node learns the node list. It is sent
only to clients below protocol 0.7 (`ReflectorClient.cpp:1362-1366`, `m_client_proto_ver < ProtoVer(0, 7)`).
Protocol 1, 2 and 3 clients get the nodes inside ServerInfo (100). A case that
waits for message 101 after a normal login would hang.

S2. TalkerStart and TalkerStop go to every client that selected the TG or monitors
it, including the talker itself (no except filter), and only to protocol 2.0 and
later; protocol 1 clients get the one-field form, and only when the TG is
`TG_FOR_V1_CLIENTS` (`Reflector.cpp:1409-1444`). The note said selected or
monitoring nodes.

S3. Talker silence timeout is 4 to 5 seconds, not "about 3": the test is
`diff.tv_sec > 3` (whole seconds) on a 1 s timer (`TGHandler.cpp:365-372`). Audio
packets refresh it; FlushSamples ends the over at once.

S4. A protocol error is answered by Error and the connection then waits up to 10 s
for the peer to close (`sendError`, `ReflectorClient.cpp:1212-1229`); during that
time every frame is ignored (`:487-491`). The note listed the timers but not
this reaction. Heartbeat timeouts use the same path ("TCP heartbeat timeout",
"UDP heartbeat timeout", `:1284-1300`).

S5. The heartbeat timers run from TCP accept, before any login: a connection that
sends nothing is answered with Error at 15 s. The UDP limit (120 s) also starts at
accept, so a node that logs in but never registers UDP is dropped at 120 s.

S6. An oversize frame is not answered at all: the server closes the TCP
connection at the length word (`AsyncFramedTcpConnection.cpp` `onDataReceived`),
before login at frame_len above 64. A frame_len of 0 delivers an empty frame only
when a further byte arrives (the empty frame is handed on by the `else` branch of
the next loop turn), then "Protocol error".

S7. Messages of type 100 and above before login are ignored with a log line,
without Error and without closing (a FIXME in the source:
`ReflectorClient.cpp:515-528`). Unknown message types are ignored by both ends
(`default:` branches), so a future type never breaks an old peer.

S8. Version handling has a dead branch and no loop guard: after ProtoVerDowngrade
the server stays in "expect ProtoVer", so the node may send ProtoVer again as
often as it likes, and the "Downgrade failed" Error in
`handleMsgProtoVer` is unreachable (`ReflectorClient.cpp:591-662`). The current
node does not comply with a downgrade at all (`ReflectorLogic.cpp:1226-1255`, under
`#if 0`); it disconnects. `ProtoVer::operator!=` compares only the major
number (`ProtoVer.h:140-143`).

S9. Failures that look the same on the wire: wrong key, unknown user, a user whose
password group is missing and a second login with a callsign already connected all
answer Error "Access denied" (`ReflectorClient.cpp:719-783,1338-1380`). A callsign
that fails `ACCEPT_CALLSIGN` answers "Invalid callsign". In the v3 certificate
path a certificate with an invalid CN callsign is disconnected without any Error
(`onSslConnectionReady`, `:411-480`).

S10. Silent fallbacks: SelectTG to a TG the node may not use makes it TG 0 and
tells the node nothing (`setTg`, `ReflectorClient.cpp:1454-1470`, FIXME in the
source); a TgMonitor set loses TG 0 and every TG the node may not monitor without
notice (`handleTgMonitor:886-916`). A node that leaves a TG with SelectTG while it is
the talker produces FlushSamples to the other members (`:856-884`) but, as far as the
code shows, no TalkerStop (`removeClientP` clears the talker without the update
callback, `TGHandler.cpp:386-401`): SVXE-8 records what the real server does.

S11. Order of the v3 start: AuthOk, ServerInfo, then the node sends NodeInfo
(111) with its AES key, and only that makes the server send StartUdpEncryption
(114); then the node registers UDP (counter 0, AAD with client id, plaintext
Heartbeat) and the server answers with a UDP Heartbeat at once, which is what the
node waits for before it is "connected" (`ReflectorClient.cpp:918-937`,
`ReflectorLogic.cpp:1983-2005`, `Reflector.cpp:1208-1212`). The client id is
allocated at TCP accept, so unauthenticated sockets also use up ids
(`ReflectorClient.cpp:397-408`).

S12. In v3 the password challenge still exists: it is the fallback after the CSR
exchange when the node has no signed certificate (`handleMsgClientCsr`,
`:786-853`), inside TLS. The manual calls AUTH_KEY deprecated, the code keeps it
fully working, and the rig can run without any CA signing step. The
server also rejects a CSR whose callsign or e-mail fails the policy with an
Error that names the reason (`Reflector.cpp:853-866`).

S13. The reflector builds its UDP datagrams inside `assert(...)`
(`Reflector.cpp:527,548`: `assert(header.pack(ss) && msg.pack(ss))`). With
`-DNDEBUG` it would send empty datagrams. The project guards against this on
purpose by overriding the release flags to `-O3` only
(`CMakeLists.txt:61-72`); a Dockerfile must not add `-DNDEBUG` (the draft does not).

S14. Audio rules not in the note: an Audio message with an empty payload never
claims the floor; audio from a node in TG 0 is ignored; a blocked node (after
`SQL_TIMEOUT`) stays blocked while it keeps sending audio, because every audio
packet refreshes the block time (`ReflectorClient.cpp:312-321,336-350,1261-1315`); and
AllSamplesFlushed goes back to whoever sent FlushSamples, talker or not
(`Reflector.cpp:1344-1359`).

S15. Source revision: the pinned commit is master after release 26.05.2, not the
release itself; the HTTP admin API of the ChangeLog (1.11.0) is in it.

S16. Headless audio is narrower than the note's wording suggests: the only
non-hardware device is `udp:`, there is no file or wav device, only 16000 and
48000 are valid `CARD_SAMPLE_RATE` values (an 8 kHz node is a recompile with
`INTERNAL_SAMPLE_RATE`), and the UDP device defaults to two interleaved channels,
so a mono tone needs `CARD_CHANNELS=1` on the node.

S17. Parser looseness a hostile peer can use (tests, not features): body parsing
does not check for trailing bytes; the bound checks in the string and vector
unpackers compare a u16 with the u16 maximum and so never fire
(`AsyncMsg.h:431,481,538`); a string is read into a stack array of the claimed length
(up to 64 KiB). Truncated bodies are caught (the read fails) and answered with
"Illegal MsgXxx protocol message received", except that the vector and set
unpackers ignore a failed read of their own count word (`AsyncMsg.h:479-481`), so
a body that ends exactly before a vector gives an undefined count: such a case is
not reproducible and is not written.

## 4. Cases for the future edge

All of these are cases FOR THE FUTURE EDGE: DV-Router (or any implementation)
listening on a reflector port as a SvxReflector-compatible server, driven by the
tester. Not runnable now. Layout: stimulus, expected, pass. "R" = identical to the
reference `svxreflector` required; "D" = a difference is allowed but must be
recorded as a finding (as `web.finding()` does for the web unit). Callsigns are
N0TEST-1, N0TEST-2, N0TEST-3 (match the default `ACCEPT_CALLSIGN`), password
`<key>` is a run secret, hex frames are given as `len type body`.

Two harness levels:

* Level P (protocol): stdlib only. The tester speaks protocol 2.0 TCP and
  plaintext UDP itself (`dvtest/proto/svx.py`), so every byte is visible and
  can be mangled. Cases SVXE-1, 3 to 11 run at this level.
* Level N (real node): `svx-a` / `svx-b` (protocol 3, TLS, AES-128-GCM) connect to the
  edge; the tester drives them with tones on their RX ports and listens on their TX
  ports. AES-GCM is not in the Python standard library, so v3 UDP cannot be spoken
  by a stdlib tester (open question 1); SVXE-2 and the node variants of SVXE-6/7 use
  level N.

### SVXE-1 Login with callsign and password (protocol 2.0, HMAC)

Stimulus:
1. TCP connect to the edge port. Send ProtoVer 2.0: `00000006 0005 0002 0000`.
2. Expect AuthChallenge: `00000018 000a 0014 <20 bytes>`. Compute
   `digest = HMAC-SHA1(key=<key>, data=those 20 bytes)`.
3. Send AuthResponse: `00000022 000b 0008 "N0TEST-1" 0014 <digest>`.
4. Expect AuthOk `00000002 000c`, then ServerInfo `.. 0064`: reserved 0000,
   client_id in 1..65535, nodes containing "N0TEST-1", codecs with exactly one entry.
5. Send a UDP datagram to the same port from a new socket:
   `0001 <client_id> 0000` (Heartbeat, seq 0). Expect a UDP Heartbeat back to that
   source address and port within 1 s: `0001 <client_id> 0000`.
6. Repeat the whole login twice: the two challenges differ.

Pass (R): the order is exactly challenge, AuthOk, ServerInfo with nothing between;
the challenge is 20 bytes; the digest check accepts only the right key (the edge
must not accept a digest over another message); UDP reply carries the same client id
and sequence 0. D: the number of codec names above one; the order of nodes.

Source: `ReflectorClient.cpp:591-662` (ProtoVer, sendAuthChallenge), `:719-783`
(AuthResponse), `:1338-1380` (connectionAuthenticated), `Reflector.cpp:1208-1212`
(first UDP datagram), `ReflectorMsg.h:366-485`.

### SVXE-2 Login with TLS, CSR and fallback password (protocol 3.0), level N

Stimulus: a real node (`svx-a`, `TYPE=Reflector`, `AUTH_KEY` set, no signed certificate) is
started against the edge. The edge presents a server certificate whose SAN holds the
address the node dialled.

Expected sequence (node view, the first four are cleartext, the rest is inside TLS):
ProtoVer(3,0) `00000006 0005 0003 0000`; edge sends CAInfo (19: u16 size, sha256);
node answers StartEncryptionRequest (14) or CABundleRequest (20) first when it has
no CA file; edge sends StartEncryption (15); TLS handshake; edge sends
ClientCsrRequest (16); node sends ClientCsr (17); edge sends AuthChallenge (10);
node AuthResponse (11); edge AuthOk (12), ServerInfo (100); node NodeInfo (111);
edge StartUdpEncryption (114); node UDP register (counter 0, AAD with client id,
plaintext Heartbeat); edge UDP Heartbeat.

Pass (R): the node logs "Login OK" equivalents: the reflector's HTTP status (or the
edge's own status) lists the node with protoVer 3.0 and the node's log shows
"Using audio codec", "Using UDP cipher AES-128-GCM" and no "ERROR". Then a tone case of
SVXE-7 works between svx-a and svx-b. D: PKI details (who signs, CA bundle download).

Source: `ReflectorClient.cpp:591-716,786-853`, `ReflectorLogic.cpp:1058-1109,1300-1484,

### SVXE-3 Bad authentication

Each variant uses a fresh TCP connection and ProtoVer 2.0 unless stated. After the
Error the tester keeps the socket open and records when the edge closes it (the

| Variant | Stimulus | Expected | Strength |
|---------|----------|----------|----------|
| a wrong key | digest made with a different key | Error `00000011 000d 000d "Access denied"`; no AuthOk, no ServerInfo | R text |
| b unknown user | AuthResponse "N0TEST-9", not in USERS | Error "Access denied" (same bytes as a) | R text |
| c invalid callsign | AuthResponse "n0test-1" (lowercase) | Error "Invalid callsign" | R text |
| d duplicate | node 1 logged in, second connection answers the challenge correctly with the same callsign | Error "Access denied" on the second; the first connection stays up and sees no NodeLeft/NodeJoined | R |

| f ProtoVer twice | ProtoVer, then ProtoVer again before answering | Error "Protocol version expected" | R text |

| h user message first | SelectTG `00000006 006a 0000006f` right after ProtoVer, before login | no Error, no closing, nothing happens; the later normal login works | R |

### SVXE-5 Node list

Stimulus (level P): login N0TEST-1 (A); then N0TEST-2 (B); then a third socket that
sends ProtoVer and stops (C, never authenticates); then B closes its TCP connection.

Expected:
* A's ServerInfo.nodes = ["N0TEST-1"]; B's = {"N0TEST-1", "N0TEST-2"} (set compare,
  the reference orders by connection, not alphabetically).
* A receives NodeJoined `.. 0066 0008 "N0TEST-2"` after B's AuthOk; B does not
  receive a NodeJoined for itself; C appears nowhere.
* After B's close A receives NodeLeft `.. 0067 0008 "N0TEST-2"` within 2 s.
* No NodeList (101) at any time for protocol 2.0 clients.
* Reference extra (D): the HTTP status shows `nodes.N0TEST-1` and, while connected,
  `nodes.N0TEST-2` with `protoVer` 2.0.

Pass (R): the three TCP facts above. Source: `ReflectorClient.cpp:1338-1380`,
`Reflector.cpp:484-496,955-998`.

| 7 | B in TG 111 while A is the talker; B SelectTG 222 | B receives UDP FlushSamples (`0066 <B id> <seq>`) |

### SVXE-7 Talker arbitration with two talkers

Setup: A, B and listener L in TG 111; D alone in TG 222 (level P; level N variant
with svx-a, svx-b and a tester-side listener).

| Step | Stimulus | Expected |
|------|----------|----------|
| 1 | A sends Audio every 20 ms | within 100 ms: TalkerStart(111, A) over TCP at A, B, L; Audio forwarded to B and L, never back to A; bytes unchanged |
| 2 | while A is active, B sends Audio | B's audio reaches nobody; no TalkerStart(B); no Error; B receives A's audio |
| 3 | A sends FlushSamples | A gets AllSamplesFlushed; A, B, L get TalkerStop(111, A); B and L get UDP FlushSamples |
| 4 | B sends Audio | TalkerStart(111, B) at A, B, L; Audio goes to A and L |
| 5 | B sends an Audio with empty payload (`0065 .. 0000`) while idle | no TalkerStart |
| 6 | D talks on 222 during step 1 | independent: TalkerStart(222, D) at D only; A, B, L unaffected |
| 7 | A talks, then stops sending without Flush | TalkerStop(111, A) and UDP Flush to B and L 4.0 to 5.5 s after the last audio |
| 8 | A talks, then closes the TCP connection | TalkerStop(111, A) then NodeLeft(A) at B and L |
| 9 | A and B send their first Audio within the same millisecond (20 trials) | in every trial exactly one TalkerStart; the loser's audio is never forwarded |

Pass (R): at most one talker per TG at any instant, equal bytes, no echo, the
timings of 1 (<100 ms), 3 (<1 s), 7 (4.0 to 5.5 s) and the order TalkerStop before

TalkerStop; A's further audio is dropped; A stays blocked as long as it sends and

All times are from the moment of the TCP connect and measured by the tester.

### SVXE-12 Observability (optional, D)

`GET /status` on the reference returns one JSON document `{"nodes": {call: {tg,
isTalker, restrictedTG, monitoredTGs, protoVer, listenOnly, ...}}}`, 404 for other
paths, 501 for non-GET/HEAD. An edge that offers the same is checked against SVXE-5
to SVXE-8; one that does not is not a failure.

## 5. How a case is judged

1. Reference step. Each case is first run against the real `svxreflector` of the
   profile `svx` (services `svxreflector`, level P tester). Its result files
   under `out/<run>/svx/` become the expectation where this document says "record".
   Nothing here replaces that step.
2. Edge step. The same case runs against the edge (`DVT_SVX_REFLECTOR_HOST`
   points the nodes and the tester at it). R items must be equal, D items are
   recorded.
3. Expected bytes are hand-derived field by field (as the unit vectors are) or
   captured from the reference; never produced by the edge's own encoder.
   Random fields (challenge, client id, audio bytes) are checked by length and
   relation, not value.
4. No case may print a password, a digest key, a client key or a PEM
   private key; digests and keys stay in `out/` as hashes only.

## 7. Capture and decoder plan

* Capture. A sniffer sidecar in the namespace of `svxreflector`, named
  `capture-svxreflector`, with the existing `x-capture` anchor and profile
  `capture-svx` (the draft is in the comment block at the end of
  `rig/compose.svx.yml`; it must live in `compose.yml` because it needs the anchor).
  It writes `out/<run>/capture/svxreflector.pcapng`.
* What a capture can show. Protocol 2.0 is fully readable (TCP frames and UDP
  headers). For protocol 3 only the cleartext start is visible (ProtoVer,
  CAInfo, StartEncryptionRequest, StartEncryption), then TLS records and UDP
  datagrams of `AAD | tag | ciphertext`, from which the decoder can still read
  counters, client id at registration, sizes and timing.
* Decoder. `dvtest/proto/svx.py` (stdlib only): `FrameSplitter` (reassembly with the
  phase limits), builders and `decode_tcp` for every message of section 2,
  `decode_udp_v2`, `split_udp_v3`, `v3_iv`. Still to write when the first capture
  exists: a pcap reader that feeds the splitter per TCP stream (the repo's
  existing pcap helpers can be reused), a printer for `out/` reports, and an optional
  GCM layer that is only imported when the `cryptography` package exists, so that a
  node's AES key from NodeInfo (visible only to the TLS endpoint, so only in a test
  that terminates TLS itself) can decrypt the UDP plaintext.
* Golden bytes come from section 2 arithmetic or from captures of the reference
  (record the commit, the codec and the capture hash), never from the decoder's own
  output.

## 9. Open questions

1. v3 UDP at byte level needs AES-128-GCM with an 8 byte tag; the standard library has
   none. Allow the `cryptography` package in the tester image for a v3 level P, or
   stay with real nodes (level N) for protocol 3?
2. Which protocol generations must the edge accept: 2.0 only plaintext (cheap, but
   svxlink 25.05 and later need `TYPE=ReflectorV2` to speak it), 3.0 with TLS, or
   both (the research note recommends 3 for production)?
3. Base image and packages are assumed (bookworm names), the Debian package that
   carries Tcl's `init.tcl` (libtcl8.6 vs tcl8.6), the exact SVXLINK `make install`
   layout (lib directory) and whether the logic plugins are found without
   `LOGIC_CORE_PATH` are untested.
4. Template keys never run: `SHORT_IDENT_INTERVAL=0` (assumed to disable
   identification), the empty `MODULES=`, `[ROOT_CA]`/`[ISSUING_CA]` needing only
   `COMMON_NAME`, `ORG`, `COUNTRY`, and `CERT_EMAIL` format.
5. Node memory and CPU (Opus encoder plus Tcl in 256 MB / 0.5 CPU) is a guess.
6. Does the VOX squelch at `VOX_THRESH=500` open on a -20 dBFS tone at 16 kHz mono
   within the filter depth, and what does the node's receiver chain (emphasis,
   limiter, default filters) do to the level? The first run must record it.
7. Whether SelectTG-while-talking sends TalkerStop (SVXE-8e) and the exact timing
   spread of the talker timeout can only be settled against the real server.

   is copied into DV-Router, as the research note's licence position requires.
